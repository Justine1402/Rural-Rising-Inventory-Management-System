# Rural Rising IMS — Frontend Structure

## Purpose of This File

This document defines the complete folder structure, component breakdown, prop
contracts, page-level specifications, and architectural rules for the
`ruriims-frontend` React application.

It is built from a full reading of:
- All 62 pages of the approved Visily prototype screenshots
- All 20 pages of the signed Software Requirements Specification (SRS)
- TECHSTACK.md and PROGRESS.md

Every feature must be built exactly according to this file — same file locations,
same component boundaries, same prop contracts — whether built manually or via
Claude Code. Always reference this file at the start of every new feature session.

---

## Core Architecture Principles (from SRS §2.2)

1. **Transaction-Ledger Model** — inventory quantities are NEVER edited directly.
   Every stock change is the result of a documented transaction.
2. **Stock-In-Use Code Tracking** — every received shipment generates a unique
   batch code that travels with the stock for its entire lifecycle.
3. **PIN Verification on every write** — all critical transactions require a
   6-digit PIN before the record is committed.
4. **Two-Stage Workflows** — Receive Order, Transfer Request, and Inventory
   Reconciliation all follow a create-then-accomplish pattern.
5. **FEFO Prioritization** — the default dashboard sort is FEFO (fewest days
   before expiration first) to ensure perishables nearest expiry are released first.

## Warehouse Configuration (from SRS §2.1)

Three permanent warehouses:
- **Main Warehouse** — Quezon City (abbreviation: **QC**)
- **Warehouse 2** — Alabang (abbreviation: **ALA**)
- **Warehouse 3** — Mandaluyong (abbreviation: **MAN**)

Temporary Warehouses are event-based (e.g., pop-up sales). Their event code uses
the first three letters of the event location (e.g., **TWH-BGC-000-001** for a
first event at BGC). Batches inside a TWH are tracked using
`TWH-[LOC]-[SKU SEQ]-[BATCH SEQ]` codes (e.g., **TWH-BGC-001-001**).

## Transaction Code Formats (from SRS §1.5 + prototype pages 17, 29, 44, 48)

| Transaction | Format | Example |
|---|---|---|
| Receive Order | `RO-[WH]-000-[SEQ]` | `RO-QC-000-003` |
| Transfer Request | `TRF-[WH]-000-[SEQ]` | `TRF-QC-000-003` |
| Issue Product | `ISS-[WH]-000-[SEQ]` | `ISS-QC-000-004` |
| Temporary Warehouse Event | `TWH-[LOC]-000-[SEQ]` | `TWH-BGC-000-001` |
| Inventory Reconciliation | `RC-[WH]-000-[SEQ]` | `RC-QC-000-003` |
| Master Product SKU | `SKU-[SEQ]` | `SKU-007` |
| Stock-In-Use Code | `SKU-[WH]-[SKU SEQ]-[BATCH SEQ]` | `SKU-QC-001-002` |
| Stock-In-Use Code (TWH) | `TWH-[LOC]-[SKU SEQ]-[BATCH SEQ]` | `TWH-BGC-001-001` |

All codes are generated by the **backend**. The frontend only displays them — it
never generates codes locally.

TWH event codes identify a Temporary Warehouse as a transaction record. TWH batch codes replace the `SKU-` prefix on Stock-In-Use codes when the warehouse holding the batch is temporary.

The Stock-In-Use Code format applies to both receive-order-generated batches and
transfer-destination batches. At TRF accomplish, one new batch is created in the destination
warehouse **per source batch deducted** by the cascade plan — not one per item. When the
destination is a permanent warehouse the code is `SKU-[DEST_WH]-[SKU_SEQ]-[BATCH_SEQ]`;
when the destination is a TWH the prefix switches to `TWH-` yielding
`TWH-[LOC]-[SKU_SEQ]-[BATCH_SEQ]`. The batch sequence is scoped per product+warehouse combination.

## PIN Verification Rules (from SRS §4.1 + prototype pages 16, 20, 28, 31, 38, 41, 43, 48, 50)

| Transaction | Who Verifies |
|---|---|
| Create Product | **Same** manager who is creating the product |
| Create Receive Order (Stage 1) | **Same** manager who created the order |
| Accomplish Receive Order (Stage 2) | **Another** manager from the **same branch** |
| Create Transfer Request (Stage 1) | **Same** manager who created the request |
| Accomplish Transfer Request (Stage 2) | **A manager from a different warehouse** — same warehouse PIN is rejected |
| Issue Product | **Same** manager who is issuing |
| Create Temporary Warehouse | **Same** manager (name auto-fills the form) |
| Close Temporary Warehouse | **Any** authorized manager |
| Submit Inventory Reconciliation | **Same** manager who reconciled |
| Confirm Inventory Reconciliation | **Another** manager from the **same branch** |

The `PinVerificationModal` UI is identical in all cases. The backend enforces
who-can-verify logic. The frontend just shows the modal and passes the response.


**Note on overlay forms vs routed pages:**
`CreateProductPage`, `ReceiveOrderFormPage` (create mode), `TransferRequestFormPage`
(create mode), and `IssueProductFormPage` open as overlays via `UIContext` — no URL
change. The Navbar buttons set `createProductFormOpen` / `receiveOrderFormOpen` /
`transferRequestFormOpen` / `issueProductFormOpen` flags respectively. `GlobalOverlays`
in `App.jsx` renders whichever overlay is open. This means there are no
`/products/create`, `/receive-orders/new`, `/transfer-requests/new`, or
`/issue-products/new` routes. Accomplish mode for Receive Orders and Transfer Requests
still uses routes (`/receive-orders/:id`, `/transfer-requests/:id`) since they need IDs.
Both list pages render beneath the overlay when the accomplish route is active —
`ReceiveOrderListPage` + `ReceiveOrderFormPage` share the `/receive-orders/:id` route,
and `TransferRequestListPage` + `TransferRequestFormPage` share `/transfer-requests/:id`.

## Context

### `AuthContext.jsx`

On mount, calls `GET /api/user` to restore session from the existing Sanctum cookie.

```js
// Value shape (reflects actual API response from Auth::user())
{
  user: {
    id: number,
    name: string,
    email: string,
    role: string,            // "admin" | "manager"
    warehouse_id: number | null,
    position_title: string | null,
  } | null,
  login: async (email, password) => void,
  logout: async () => void,
  isAuthenticated: boolean,
  loading: boolean,
}
```

### `UIContext.jsx`

Controls which form overlays are open globally, without changing the URL. Also
exposes a product refresh signal so the dashboard can re-fetch immediately after
a product is created — without navigating away.

```js
{
  receiveOrderFormOpen: boolean,
  setReceiveOrderFormOpen: function,
  createProductFormOpen: boolean,
  setCreateProductFormOpen: function,
  transferRequestFormOpen: boolean,
  setTransferRequestFormOpen: function,
  issueProductFormOpen: boolean,
  setIssueProductFormOpen: function,
  temporaryWarehouseFormOpen: boolean,
  setTemporaryWarehouseFormOpen: function,
  closeTemporaryWarehouseOverlayTwhId: number | null,  // null = closed; number = TWH id to close
  setCloseTemporaryWarehouseOverlayTwhId: function,
  temporaryWarehouseDetailOverlayTwhId: number | null, // null = closed; number = TWH id to view
  setTemporaryWarehouseDetailOverlayTwhId: function,
  productRefreshKey: number,              // increments on each successful product creation
  refreshProducts: function,              // call this to trigger a dashboard re-fetch
  receiveOrderRefreshKey: number,         // increments on each successful RO create/accomplish
  refreshReceiveOrders: function,         // call this to trigger an RO list re-fetch
  transferRequestRefreshKey: number,      // increments on each successful TRF create/accomplish
  refreshTransferRequests: function,      // call this to trigger a TRF list re-fetch
  reconciliationFormOpen: boolean,
  setReconciliationFormOpen: function,
  reconciliationRefreshKey: number,       // increments on each successful RC create/confirm
  refreshReconciliations: function,       // call this to trigger a Reconciliation list re-fetch
  userFormOpen: boolean,                  // true = open UserFormOverlay (Stage 3)
  setUserFormOpen: function,
  userDetailOverlayUserId: number | null, // null = closed; number = user id to view/edit
  setUserDetailOverlayUserId: function,
  userRefreshKey: number,                 // increments on each successful user create/update/delete
  refreshUsers: function,                 // call this to trigger a UserManagementPage re-fetch
}
```

`GlobalOverlays` in `App.jsx` renders the following overlays when their UIContext flags/IDs are set:
- `CreateProductPage` — when `createProductFormOpen` is true
- `ReceiveOrderFormPage` (create mode) — when `receiveOrderFormOpen` is true
- `TransferRequestFormPage` (create mode) — when `transferRequestFormOpen` is true
- `IssueProductFormPage` — when `issueProductFormOpen` is true
- `TemporaryWarehouseFormPage` — when `temporaryWarehouseFormOpen` is true
- `CloseTemporaryWarehousePage` — always mounted; self-guards on `closeTemporaryWarehouseOverlayTwhId !== null`
- `TemporaryWarehouseDetailPage` — always mounted; self-guards on `temporaryWarehouseDetailOverlayTwhId !== null`
- `ReconciliationFormPage` — when `reconciliationFormOpen` is true

The Navbar buttons set boolean flags for the first five. `CloseTemporaryWarehousePage` and
`TemporaryWarehouseDetailPage` open by setting the ID-carrying state to the TWH id to view.
RETURN inside each overlay clears its flag/ID via the setter — no `navigate()` call.
Each overlay calls its `onSuccess` prop (or internally calls `refreshWarehouses()`) on successful
submit to trigger the relevant list or dashboard re-fetch.

### `WarehouseContext.jsx`

Updated when the user clicks a `WarehouseTabs` item. All transaction forms
auto-fill "Warehouse" from this context.

```js
// Value shape
{
  activeWarehouse: { id: number, name: string, code: string, isTemporary: boolean,
                     transactionCode?: string, temporaryWarehouseId?: number },
  warehouses: [{ id: number, name: string, code: string, isTemporary: boolean,
                 transactionCode?: string, temporaryWarehouseId?: number }],
  setActiveWarehouse: (warehouse) => void,
  refreshWarehouses: (selectWarehouseId?: number) => void,
  // selectWarehouseId: if provided, auto-selects that TWH tab after refresh
  // (used by TemporaryWarehouseFormPage after creation). Omit to preserve current active.
}
```

Permanent warehouses are fetched from `GET /api/warehouses` when `user` becomes
non-null (i.e., after auth is confirmed). The `useEffect` depends on `[user]` — not
`[]` — so it never fires before the Sanctum session is established, and it clears the
warehouse list on logout. Temporary warehouses are appended dynamically when active.

**Role-based initialization (Step 13.75):**
- **Admin:** `warehouses` contains all permanent + active TWH entries; `activeWarehouse`
  defaults to `null` on login, representing "All Warehouses". `refreshWarehouses()` preserves
  `null` if `prev === null`, falls back to `null` (not `list[0]`) if the previously-selected
  warehouse disappears.
- **Manager:** `warehouses` is filtered to a single-entry list containing only the manager's
  assigned permanent warehouse (matched by `user.warehouse_id`; fallback to `list[0]` if not
  found); `activeWarehouse` is set to that warehouse. Manager sees no tab switcher.

## Layout Components

### `Navbar.jsx`

Persistent top bar on every protected page. Reads from `AuthContext` and
`WarehouseContext` via `useContext` — no props needed.

**Left:** "RURAL RISING" brand text.

**Center-left action buttons:**

Default state (permanent warehouse active):
- `+ Create Product` → opens `CreateProductPage` overlay via `UIContext` (no URL change)
- `+ Receive Order` → opens `ReceiveOrderFormPage` overlay via `UIContext` (no URL change)
- `+ Transfer Request` → opens `TransferRequestFormPage` overlay via `UIContext` (no URL change)
- `+ Issue Product` → opens `IssueProductFormPage` overlay via `UIContext` (no URL change)
- `+ Create Temporary Warehouse` → opens `TemporaryWarehouseFormPage` overlay via `UIContext` (no URL change)

Contextual button changes on list pages:

**Right:** Settings icon (⚙) + circular user avatar → click opens `ProfileModal`.
Active warehouse name displayed as text in the top-right area.

The Settings icon (⚙) is visible only to admin users. Clicking it opens a
small dropdown containing a "Manage Accounts" item that navigates to
`/admin/users`. Click-outside closes the dropdown.

**Avatar dropdown menu items (top to bottom):**
1. User name + email (read-only header, non-clickable)
2. "View Profile" — opens `ProfileModal`
3. "Log out" — calls `logout()` then navigates to `/login`

### `StockInUseModal.jsx`

Batch picker for Transfer Request and Issue Product flows. Opens when the user
**clicks the Stock-In-Use Code cell** of a product row in the form table — it
does NOT open automatically. One `StockInUseModal` interaction is needed per
product row, called individually after `AddProductsModal` closes.

Title format: "Stock-In-Use: SKU-001" (where SKU-001 is the selected product's SKU)
Columns: Code | Harvest Date | Quantity | Category

Props:
```js
isOpen        boolean
skuCode       string    // e.g. "SKU-001" — used in the modal title
warehouseId   number    // source warehouse to fetch available batches from
onSelect      function  // receives { id, code, harvest_date, quantity, category }
onClose       function
```

Used by: `TransferRequestFormPage`, `IssueProductFormPage`

**Product selection flow for Transfer and Issue (identical for both):**
1. User clicks "Add Product" → `AddProductsModal` opens
2. User selects one or more master SKUs → clicks SELECT
3. `AddProductsModal` closes → selected products appear in the product table
   with Stock-In-Use Code column blank
4. User clicks the Stock-In-Use Code cell of a product row → `StockInUseModal`
   opens for that specific SKU
5. User selects a batch → row is populated (Stock-In-Use Code, Harvest Date auto-fill)
6. Repeat step 4–5 for each remaining product row

### `TransferRequestFormPage` (proto p.23-33, SRS §3.5.3-3.5.6)

**Create mode** (UIContext overlay — no URL change):

Header: RETURN button + "Create Transfer Request" title

Auto-filled (read-only):

- Date Requested: today's date

User-filled:
- Source Warehouse (dropdown: 3 permanent warehouses — selecting one disables it
  as an option in Destination Warehouse)
- Destination Warehouse (dropdown: 3 permanent warehouses + any active Temporary
  Warehouses — selecting one disables it in Source Warehouse)

Product Details section — **two-step flow:**
1. "Add Product" button → `AddProductsModal` opens (select one or more master SKUs)
2. SELECT closes `AddProductsModal` → selected products appear in the product table
   with Stock-In-Use Code column blank
3. User clicks the Stock-In-Use Code cell for a product row → `StockInUseModal`
   opens for that SKU, showing available batches in the source warehouse
4. User selects a batch → row is populated:
   Product SKU | Product Name | Stock-In-Use Code | Available |
   Quantity Requested (user input) | Harvest Date (auto from batch)
   — Available cell shows `{batch_quantity} {unit}` (e.g., "100 kg"); blank when no batch selected
5. Repeat step 3–4 for each product row

CREATE button → `PinVerificationModal` (same manager) → on verified →
"Created TRF-QC-000-003" confirmation label appears → record saved as Incomplete.

**Per-row quantity validation — create mode — three tiers:**
- **No feedback** — Qty Requested ≤ selected batch quantity. Single-batch deduction.
- **Gray cascade hint** — Qty Requested exceeds selected batch but is within the warehouse
  total across all batches. Inline text below input: "Will draw from N batch(es) — preview"
  (the "preview" link opens `CascadePreviewModal` showing the exact batch draw plan). CREATE
  is enabled.
- **Red error, submit disabled** — Qty Requested exceeds warehouse total across all batches.
  Text: "Only {total} {unit} available across all batches in this warehouse."

If a quantity is entered but no batch is selected, helper text shows: "Select a
Stock-In-Use Code first."

**Cascade behavior (create mode):**
When typed quantity exceeds the selected batch, the backend draws from neighboring batches
in the same warehouse by nearest harvest date to the selected batch, with oldest-first
(FIFO) tiebreak for equal distances. On CREATE, the cascade plan is computed and stored
as `transfer_request_batch_deductions` rows. Stock is **not yet deducted** at create
time — the plan records the requester's intent only.

**Accomplish mode** (`/transfer-requests/:id`):

Header title is the TRF code (e.g., "TRF-QC-000-003"). Pre-filled read-only
fields: Requested By, Date Requested, Source Warehouse, Destination Warehouse.
Blank editable fields: Verified By, Date Received.

Product table: Product SKU | Product Name | Stock-In-Use Code | Available |
Quantity Requested (read-only) | Quantity Received (user inputs) | Harvest Date
— Available cell shows `{batch_quantity} {unit}` loaded from the show API response
(no extra fetch; `batch_quantity` is included per item in `GET /api/transfer-requests/{id}`)

**Per-row quantity validation — accomplish mode — three tiers:**
- **No feedback** — Qty Received ≤ selected batch quantity.
- **Gray cascade hint** — Qty Received exceeds selected batch but is within warehouse total.
  Inline text: "Will draw from N batch(es) — preview" (opens `CascadePreviewModal`).
  ACCOMPLISH is enabled.
- **Red error, submit disabled** — Qty Received exceeds warehouse total.

The accomplish form fetches fresh batch data per product on load (parallel
`GET /stock-in-use` calls per unique product code), so the cascade preview reflects
current stock at accomplish time, not the stale create-time plan.

**Cascade recomputation at accomplish time:**
The stored `transfer_request_batch_deductions` plan is treated as the requester's original
intent, not a literal execution plan. At accomplish time the backend:
1. Deletes the stored `transfer_request_batch_deductions` rows for each item.
2. Recomputes the cascade plan against current stock using `quantity_received` (the
   verifier's input) and `requested_stock_in_use_id` (to honor the original batch preference).
3. Inserts new `transfer_request_batch_deductions` rows from the recomputed plan.
4. Deducts from each source batch per the new plan.
5. Creates one destination batch per source batch deducted, copying the source batch's
   harvest date. Two source batches drawn → two destination batches created.

The `transfer_request_items` row's `requested_stock_in_use_id` and `quantity_requested`
are never modified at accomplish time — they preserve the requester's original intent for
audit purposes.

**Edge case — anchor batch depleted between create and accomplish:**
If `requested_stock_in_use_id` has been fully depleted since the TRF was created, the
planner falls back to FIFO across all remaining non-zero batches in the source warehouse
(oldest harvest date first), rather than erroring out.

ACCOMPLISH button → `PinVerificationModal` — PIN verification on ACCOMPLISH enforces two guards:
- **Same-user check (all roles):** The verifying user cannot be the user who created the request.
- **Same-warehouse check (managers only):** The verifying manager must be from a different warehouse than the one that created the request. Admins (`warehouse_id = null`) are not subject to this check because they are not assigned to any branch.

→ on verified → "Accomplished TRF-QC-000-003" label → status changes to Complete
→ stock deducted from source warehouse per recomputed cascade plan, new batches
added to destination warehouse (one per source batch deducted).

## Standard Page Patterns

### All list pages:
1. `useEffect` on mount → fetch data from API
2. Store in `useState`; show loading indicator while fetching
3. Render inline `<table>` markup with columns per spec above (no shared DataTable component)
4. `useState` for `error` — show inline red message if fetch fails
5. `onRowClick` → `useNavigate` to form/detail route
6. **Single-row select behavior applies to: `ReceiveOrderListPage`,
   `TransferRequestListPage`, and `ReconciliationListPage`**. In each of these,
   maintain a `selectedRow` state. When a qualifying row is selected (Incomplete
   for Receive/Transfer; Pending Review for Reconciliation), the corresponding
   Navbar/content-area button changes its label and target route. Clicking the
   selected row again deselects it.

### All form pages:
1. If `:id` param exists → fetch record on mount, pre-fill all fields (accomplish/view mode)
2. If no param → empty form; auto-fill user, date, and warehouse from context
3. Local `useState` for all form fields
4. "Add Product" → `AddProductsModal` → selected products added to local array
   in state, with Stock-In-Use Code initially blank
5. For Transfer and Issue: user clicks each product's Stock-In-Use Code cell →
   `StockInUseModal` opens for that row → on select, that row's data is updated
6. Submit/action button → `PinVerificationModal` → on `onVerify` callback → fire
   API call
7. On API success → `useNavigate` back to the appropriate list or dashboard route

### Error handling (all pages):
```js
const [error, setError] = useState(null);
const [loading, setLoading] = useState(false);

try {
  setLoading(true);
  await api.post('/endpoint', payload);
  navigate('/route');
} catch (err) {
  setError(err.response?.data?.message ?? 'Something went wrong. Please try again.');
} finally {
  setLoading(false);
}
```

Display `error` as a red inline message above the submit button. Disable the
submit button while `loading` is true.

## Styling Rules

All styling uses Tailwind CSS utility classes for layout, spacing, and typography. Brand colors are applied in one of two ways:
- **Non-interactive elements** (table headers, nav bar): inline `style={{ backgroundColor: '#hex' }}` per DESIGN.md.
- **Interactive elements with hover states** (buttons, active tabs): the `.btn-brand` / `.btn-brand-outline` classes defined in `src/index.css`. These override Tailwind's arbitrary-value classes (`bg-[#hex]`), which are no longer used anywhere in the codebase.
- **Status badges are a documented exception.** `StatusBadge` uses Tailwind named pastel classes (`bg-{color}-100 text-{color}-800/700`) for green, amber, and red tiers to maintain the prototype's soft status-indicator visual language. The brand palette (`#1A381E`, `#409645`, etc.) is reserved for primary UI surfaces (nav, table headers, buttons) where it carries identity weight.

**Brand colors — see DESIGN.md (source of truth for all brand hex values). Do NOT use `bg-green-700`, `bg-green-800`, or any Tailwind green presets for brand surfaces. Tailwind arbitrary-value brand color classes (`bg-[#hex]`, `hover:bg-[#hex]`) are not used.**
- Navbar / page headers / table headers: `style={{ backgroundColor: '#1A381E' }}` (dark green)
- Buttons / active tabs: `className="btn-brand"` (medium green `#409645`, hover `#367a38`)
- Ghost bordered buttons on dark bg: `className="btn-brand-outline"` (hover shows `#409645`)

**Buttons:**
- Primary filled: `btn-brand text-white px-4 py-2 rounded disabled:opacity-50 disabled:cursor-not-allowed`
- Secondary outlined: `border border-[#409645] text-[#409645] px-4 py-2 rounded hover:bg-green-50`

**Form fields:**

## API Call Pattern

All calls go through `src/api/axios.js`. Never use `fetch` directly.

```js
import api from '../../api/axios';

const response = await api.post('/receive-orders', payload);
```

`getCsrfCookie()` is called **once during login only**. The Sanctum session cookie
persists for all subsequent requests in the session. Do NOT call it before every
individual request.
