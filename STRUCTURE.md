# Rural Rising IMS — Frontend Structure

## Purpose of This File

This document defines the complete folder structure, component breakdown, prop
contracts, page-level specifications, and architectural rules for the
`ruriims-frontend` React application.

It is built from a full reading of:
- All 62 pages of the approved Visily prototype screenshots
- All 20 pages of the signed Software Requirements Specification (SRS)
- TECHSTACK.md and PROGRESS.md

Every feature must be built exactly according to this file — same file locations,
same component boundaries, same prop contracts — whether built manually or via
Claude Code. Always reference this file at the start of every new feature session.

---

## Core Architecture Principles (from SRS §2.2)

1. **Transaction-Ledger Model** — inventory quantities are NEVER edited directly.
   Every stock change is the result of a documented transaction.
2. **Stock-In-Use Code Tracking** — every received shipment generates a unique
   batch code that travels with the stock for its entire lifecycle.
3. **PIN Verification on every write** — all critical transactions require a
   6-digit PIN before the record is committed.
4. **Two-Stage Workflows** — Receive Order, Transfer Request, and Inventory
   Reconciliation all follow a create-then-accomplish pattern.
5. **FEFO Prioritization** — the default dashboard sort is FEFO (fewest days
   before expiration first) to ensure perishables nearest expiry are released first.

---

## Warehouse Configuration (from SRS §2.1)

Three permanent warehouses:
- **Main Warehouse** — Quezon City (abbreviation: **QC**)
- **Warehouse 2** — Alabang (abbreviation: **ALA**)
- **Warehouse 3** — Mandaluyong (abbreviation: **MAN**)

Temporary Warehouses are event-based (e.g., pop-up sales). Their code prefix uses
the first three letters of the event location (e.g., **TWH-BGC-000-001** for BGC).

## Transaction Code Formats (from SRS §1.5 + prototype pages 17, 29, 44, 48)

| Transaction | Format | Example |
|---|---|---|
| Receive Order | `RO-[WH]-000-[SEQ]` | `RO-QC-000-003` |
| Transfer Request | `TRF-[WH]-000-[SEQ]` | `TRF-QC-000-003` |
| Issue Product | `ISS-[WH]-000-[SEQ]` | `ISS-QC-000-004` |
| Temporary Warehouse | `TWH-[LOC]-000-[SEQ]` | `TWH-BGC-000-001` |
| Inventory Reconciliation | `RC-[WH]-000-[SEQ]` | `RC-QC-000-003` |
| Master Product SKU | `SKU-[SEQ]` | `SKU-007` |
| Stock-In-Use Code | `SKU-[WH]-[SKU SEQ]-[BATCH SEQ]` | `SKU-QC-001-002` |

All codes are generated by the **backend**. The frontend only displays them — it
never generates codes locally.

## PIN Verification Rules (from SRS §4.1 + prototype pages 16, 20, 28, 31, 38, 41, 43, 48, 50)

| Transaction | Who Verifies |
|---|---|
| Create Product | **Same** manager who is creating the product |
| Create Receive Order (Stage 1) | **Same** manager who created the order |
| Accomplish Receive Order (Stage 2) | **Another** manager from the **same branch** |
| Create Transfer Request (Stage 1) | **Same** manager who created the request |
| Accomplish Transfer Request (Stage 2) | **A manager from a different warehouse** — same warehouse PIN is rejected |
| Issue Product | **Same** manager who is issuing |
| Create Temporary Warehouse | **Same** manager (name auto-fills the form) |
| Close Temporary Warehouse | **Any** authorized manager |
| Submit Inventory Reconciliation | **Same** manager who reconciled |
| Confirm Inventory Reconciliation | **Another** manager from the **same branch** |

The `PinVerificationModal` UI is identical in all cases. The backend enforces
who-can-verify logic. The frontend just shows the modal and passes the response.

## Context

### `AuthContext.jsx`

On mount, calls `GET /api/user` to restore session from the existing Sanctum cookie.

```js
// Value shape
{
  user: {
    id: number,
    name: string,           // e.g. "James Clark"
    email: string,
    position: string,       // e.g. "Main Warehouse Manager"
    employeeId: string,     // e.g. "2361927"
    warehouseId: number,
    warehouseName: string,  // e.g. "Main Warehouse (Quezon City)"
    warehouseCode: string,  // e.g. "QC"
    role: string,           // "admin" | "manager"
  } | null,
  login: async (email, password) => void,
  logout: async () => void,
  isAuthenticated: boolean,
}
```

### `WarehouseContext.jsx`

Updated when the user clicks a `WarehouseTabs` item. All transaction forms
auto-fill "Warehouse" from this context.

```js
// Value shape
{
  activeWarehouse: { id: number, name: string, code: string, isTemporary: boolean },
  warehouses: [{ id: number, name: string, code: string, isTemporary: boolean }],
  setActiveWarehouse: (warehouse) => void,
}
```

Permanent warehouses are fetched from `GET /api/warehouses` on app load.
Temporary warehouses are appended dynamically when they are active/open.

## Shared Components

### `PinVerificationModal.jsx`

Six individual square input boxes in a row, each masked with `*` on entry.
Centered overlay, dimmed background. X button closes without verifying.

Elements (SRS §3.3.4, prototype p.8):
- Title: "Transaction Verification"
- Subtitle: "Enter your 6-Digit Code"
- 6 square inputs, each accepts one digit, auto-advances focus
- Success state: "Transaction verified successfully!" in green below inputs
- CLEAR button — resets all inputs to empty
- VERIFY button — submits the PIN to the backend
- X button top-right — closes without verifying

Props:
```js
isOpen     boolean
onVerify   function   // called when backend confirms PIN is valid
onClose    function   // called when X is clicked
```

Used by: `CreateProductPage`, `ReceiveOrderFormPage` (Stage 1 and Stage 2),
`TransferRequestFormPage` (Stage 1 and Stage 2), `IssueProductFormPage`,
`TemporaryWarehouseFormPage`, `CloseTemporaryWarehousePage`,
`ReconciliationFormPage`, `ReconciliationReviewPage`

---

### `AddProductsModal.jsx`

Master product picker. Shows all master SKU products in the system. Columns:
Product Code | Product Name | Unit | Category. Multiple rows can be selected
simultaneously (highlighted green). SELECT button confirms all selections at once.

After SELECT closes the modal, selected products appear in the calling form's
product table with their Stock-In-Use Code column **blank**. The user then clicks
each product's Stock-In-Use Code cell to open `StockInUseModal` for that row.

Props:
```js
isOpen      boolean
onSelect    function   // receives [{ productCode, productName, unit, category }]
onClose     function
```

Used by: `ReceiveOrderFormPage`, `TransferRequestFormPage`, `IssueProductFormPage`

---

### `StockInUseModal.jsx`

Batch picker for Transfer Request and Issue Product flows. Opens when the user
**clicks the Stock-In-Use Code cell** of a product row in the form table — it
does NOT open automatically. One `StockInUseModal` interaction is needed per
product row, called individually after `AddProductsModal` closes.

Title format: "Stock-In-Use: SKU-001" (where SKU-001 is the selected product's SKU)
Columns: Code | Harvest Date | Quantity | Category

Props:
```js
isOpen        boolean
skuCode       string    // e.g. "SKU-001" — used in the modal title
warehouseId   number    // source warehouse to fetch available batches from
onSelect      function  // receives { code, harvestDate, quantity, category }
onClose       function
```

Used by: `TransferRequestFormPage`, `IssueProductFormPage`

**Product selection flow for Transfer and Issue (identical for both):**
1. User clicks "Add Product" → `AddProductsModal` opens
2. User selects one or more master SKUs → clicks SELECT
3. `AddProductsModal` closes → selected products appear in the product table
   with Stock-In-Use Code column blank
4. User clicks the Stock-In-Use Code cell of a product row → `StockInUseModal`
   opens for that specific SKU
5. User selects a batch → row is populated (Stock-In-Use Code, Harvest Date auto-fill)
6. Repeat step 4–5 for each remaining product row

## Page Specifications

### `LoginPage` (proto p.3-4, SRS §3.1.1)

Centered card titled "Rural Rising IMS". Fields: Email (placeholder: "Enter your
email"), Password (show/hide toggle, placeholder: "Enter your password"), Remember me
checkbox, Forgot password? link. Button: "Sign in" (green, full-width). Rural
Rising PH logo at bottom of the card.

Flow: `getCsrfCookie()` → `POST /api/login` → set user in `AuthContext` → navigate to `/`

---

### `UserManagementPage` (admin only)

Accessible only to users with `role === "admin"`. Reached via the Settings icon
(⚙) in the Navbar. Non-admin users are redirected to `/` if they attempt to
access `/admin/users` directly.

**Account list table columns:**
Name | Email | Position | Assigned Warehouse | Status | Actions

**Actions per row:**
- **Disable / Enable** toggle — activates or deactivates the account. Disabled
  accounts cannot log in.
- **Edit** — opens an inline form to update name, email, assigned warehouse, or
  position.

**"+ Add Account" button** (top of page):
Opens an inline form with fields:
- Name (text)
- Email (text)
- Password (text — admin sets the initial password)
- Position (text, e.g., "Main Warehouse Manager")
- Assigned Warehouse (dropdown: Main Warehouse | Warehouse 2 | Warehouse 3)

Submitting creates the account via `POST /api/admin/users`. No PIN verification
is required for account management — admin access is the authorization.

Managers cannot self-register. There is no public registration flow anywhere in
the system.

---

### `DashboardPage` (proto p.4, 9-11, 21-22, 33, 39, 42, 52, SRS §3.2)

The primary view after login. The `Inventory` dropdown in the Navbar switches
the main content area between: the inventory table, the Receive Orders list, the
Transfer Requests list, and the Inventory Reconciliation list. These are all
rendered inside `DashboardPage` — they are not separate full pages.

**Issue Product list is also accessible from the main dashboard.** Issued product
transactions are visible as part of the dashboard's transaction record area.
There is no separate `IssueProductListPage` — issue history is surfaced here and
in the Reports section.

---

#### Standard Inventory Table (permanent warehouse active)

**Default columns (FIFO / LIFO mode):**
Name | Main Warehouse | Alabang Warehouse | Mandaluyong Warehouse | Harvest Date | Status

**FEFO mode columns:**
Name | Main Warehouse | Alabang Warehouse | Mandaluyong Warehouse | Days Before Expiration | Status

The 5th column header changes based on the active sort mode. Sorting behavior:
- **FIFO** — ascending harvest date (oldest first)
- **FEFO** — ascending days before expiration; can be negative for expired stock
- **LIFO** — descending harvest date (newest first)

`All Products` dropdown filters rows by category. Table is read-only.

---

#### Temporary Warehouse View (TWH tab active)

When `WarehouseContext.activeWarehouse.isTemporary === true`, the dashboard
switches to a simplified table:

**Columns:** Name | Quantity | Harvest Date | Status

All rows will initially show "Out of Stock" until stock is transferred in via
Transfer Request. The `All Products` dropdown, sort mode dropdown, and `Inventory`
dropdown remain in the Navbar. The Navbar action buttons change to only:
`+ Issue Product` | `+ Transfer Request` | `+ Close Temporary Warehouse`

### `ReceiveOrderFormPage` (proto p.12-21, SRS §3.4.3-3.4.6)

**Create mode** (`/receive-orders/new`):

Header: RETURN button (left) + "Receive Order" title (right)

Form fields:
- Supplier Name (text input)
- Order Cost (auto-computed from product costs, PHP, read-only display)
- Delivery Fee (PHP number input, user enters)
- Date Ordered (date picker — calendar dropdown on click)
- Date Arrived (date picker — **disabled** in Stage 1, enabled in Stage 2)
- Total (auto-computed: Order Cost + Delivery Fee, read-only)

Product Details section:
- "Add Product" button → opens `AddProductsModal`
- After selection, product rows appear in table:
  Product Code | Product Name | Quantity Ordered (user input) |
  Quantity Arrived (disabled in Stage 1, defaults to 0) |
  Harvest Date (date picker per row, calendar icon) |
  Product Cost (PHP, user input)
- Order Cost auto-updates as product costs are entered/changed

CREATE button → `PinVerificationModal` (same manager) → on verified →
"Created RO-QC-000-003" confirmation label appears next to CREATE button →
record saved as Incomplete status.

**Accomplish mode** (`/receive-orders/:id`):

The Receiving Order # is shown as the header title (e.g., "RO-QC-000-003").
All header fields are pre-filled and read-only. In the product table, only
**Date Arrived** (header field) and **Quantity Arrived** (per product row) are
editable — all other fields are read-only.

COMPLETE button → `PinVerificationModal` (different manager, same branch) →
on verified → "Accomplished RO-QC-000-003" confirmation label appears →
status changes to Accomplished → Stock-In-Use codes generated per product line
(format: `SKU-QC-001-002`) → inventory quantities added to the warehouse.

### `TransferRequestFormPage` (proto p.23-33, SRS §3.5.3-3.5.6)

**Create mode** (`/transfer-requests/new`):

Header: RETURN button + "Create Transfer Request" title

Auto-filled (read-only):
- Requested By: logged-in manager's name
- Date Requested: today's date

User-filled:
- Source Warehouse (dropdown: 3 permanent warehouses — selecting one disables it
  as an option in Destination Warehouse)
- Destination Warehouse (dropdown: 3 permanent warehouses + any active Temporary
  Warehouses — selecting one disables it in Source Warehouse)

Product Details section — **two-step flow:**
1. "Add Product" button → `AddProductsModal` opens (select one or more master SKUs)
2. SELECT closes `AddProductsModal` → selected products appear in the product table
   with Stock-In-Use Code column blank
3. User clicks the Stock-In-Use Code cell for a product row → `StockInUseModal`
   opens for that SKU, showing available batches in the source warehouse
4. User selects a batch → row is populated:
   Product SKU | Product Name | Stock-In-Use Code | Unit |
   Quantity Requested (user input) | Harvest Date (auto from batch)
5. Repeat step 3–4 for each product row

CREATE button → `PinVerificationModal` (same manager) → on verified →
"Created TRF-QC-000-003" confirmation label appears → record saved as Incomplete.

**Accomplish mode** (`/transfer-requests/:id`):

Header title is the TRF code (e.g., "TRF-QC-000-003"). Pre-filled read-only
fields: Requested By, Date Requested, Source Warehouse, Destination Warehouse.

## Standard Page Patterns

### All list pages:
1. `useEffect` on mount → fetch data from API
2. Store in `useState`; show loading indicator while fetching
3. Render `DataTable` with columns per spec above
4. `useState` for `error` — show inline red message if fetch fails
5. `onRowClick` → `useNavigate` to form/detail route
6. **Single-row select behavior applies to: `ReceiveOrderListPage`,
   `TransferRequestListPage`, and `ReconciliationListPage`**. In each of these,
   maintain a `selectedRow` state. When a qualifying row is selected (Incomplete
   for Receive/Transfer; Pending Review for Reconciliation), the corresponding
   Navbar/content-area button changes its label and target route. Clicking the
   selected row again deselects it.

### All form pages:
1. If `:id` param exists → fetch record on mount, pre-fill all fields (accomplish/view mode)
2. If no param → empty form; auto-fill user, date, and warehouse from context
3. Local `useState` for all form fields
4. "Add Product" → `AddProductsModal` → selected products added to local array
   in state, with Stock-In-Use Code initially blank
5. For Transfer and Issue: user clicks each product's Stock-In-Use Code cell →
   `StockInUseModal` opens for that row → on select, that row's data is updated
6. Submit/action button → `PinVerificationModal` → on `onVerify` callback → fire
   API call
7. On API success → `useNavigate` back to the appropriate list or dashboard route

### Error handling (all pages):
```js
const [error, setError] = useState(null);
const [loading, setLoading] = useState(false);

try {
  setLoading(true);
  await api.post('/endpoint', payload);
  navigate('/route');
} catch (err) {
  setError(err.response?.data?.message ?? 'Something went wrong. Please try again.');
} finally {
  setLoading(false);
}
```

Display `error` as a red inline message above the submit button. Disable the
submit button while `loading` is true.

## API Call Pattern

All calls go through `src/api/axios.js`. Never use `fetch` directly.

```js
import api from '../../api/axios';

const response = await api.post('/receive-orders', payload);
```

`getCsrfCookie()` is called **once during login only**. The Sanctum session cookie
persists for all subsequent requests in the session. Do NOT call it before every
individual request.
